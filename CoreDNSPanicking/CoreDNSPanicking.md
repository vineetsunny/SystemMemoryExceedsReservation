# CoreDNSPanicking

PrometheusRule Source: `dns` · Alert Severity: `Warning` · Pending Period: `5m`

---

## Meaning:

This alert means that CoreDNS has encountered one or more panic events in the last 10 minutes.
The alert is triggered when the `coredns_panics_total` metric increases, which indicates that CoreDNS has experienced a panic.

***Expression***

```bash
increase(coredns_panics_total[10m]) > 0
```

---

## Impact:

- Applications may experience DNS lookup failures, connection errors, or request timeouts.
- DNS pod restarts may increase, potentially causing intermittent DNS resolution failures.
- DNS resolution may resume, but repeated panics can cause recurring disruptions.

---

## Diagnosis:

| Command | What to look for | Action |
|---|---|---|
| `oc exec -n openshift-monitoring prometheus-k8s-0 -c prometheus -- curl -s 'http://localhost:9090/api/v1/query?query=coredns_panics_total'` | Check whether the `coredns_panics_total` counter is increasing. | Compare consecutive values and verify whether the metric is generated by CoreDNS or a custom exporter. |
| `oc exec -n openshift-monitoring prometheus-k8s-0 -c prometheus -- curl -s 'http://localhost:9090/api/v1/query?query=increase(coredns_panics_total%5B10m%5D)'` | A value greater than `0` indicates an increase in the counter over the last 10 minutes. | Identify the affected metric series and correlate the increase with pod logs and restart events. |
| `oc get pods -n openshift-dns -l dns.operator.openshift.io/owning-dns=default -o wide` | Check for pods that are not Running or Ready, and identify increasing restart counts. | Identify affected pods and nodes for further investigation. |
| `oc describe pod <pod-name> -n openshift-dns` | Check container states, restart counts, probe failures, resource issues, and Events. | Investigate any container termination, readiness failure, or resource-related issue. |
| `oc logs -n openshift-dns <pod-name> -c dns --since=30m` | Look for panic messages, stack traces, plugin errors, or unexpected runtime failures. | Correlate log timestamps with the alert and identify the possible cause. |
| `oc logs -n openshift-dns <pod-name> -c dns --previous` | Check logs from the previous container instance for panic messages or errors before a restart. | Use the logs to investigate the reason for the previous container termination. |
| `oc get co dns` | Check whether the DNS Operator is Available, Progressing, or Degraded. | Investigate DNS Operator conditions if the component is unhealthy. |
| `oc get dns.operator.openshift.io default -o yaml` | Check the DNS Operator management state, conditions, and configuration. | Identify configuration issues or unexpected management-state changes. |
| `oc get daemonset dns-default -n openshift-dns` | Compare desired, current, ready, and available pod counts. | Investigate missing or unavailable CoreDNS pods. |
| `oc describe daemonset dns-default -n openshift-dns` | Check DaemonSet events, rollout issues, and container configuration. | Investigate unexpected changes, scheduling failures, or unsuccessful rollouts. |
| `oc exec -n <application-namespace> <pod-name> -- getent hosts kubernetes.default.svc` | Check whether internal service DNS resolution succeeds or returns errors or timeouts. | If resolution fails, investigate DNS pod health, service connectivity, and CoreDNS logs. |
| `oc exec -n <application-namespace> <pod-name> -- getent hosts example.com` | Check whether external DNS resolution succeeds, where external resolution is expected and permitted. | Investigate upstream forwarding and DNS connectivity if resolution fails. |



---

## Mitigation

1. Remove any unauthorized custom containers, exporter configurations, or modified proxy arguments from the dns-default DaemonSet. For the lab setup, allow the Operator to reconcile the DaemonSet after restoring managed state.
2. Ensure the dns-default DaemonSet rollout completes successfully and all expected CoreDNS pods are Ready.
3. If an affected pod does not recover automatically after the underlying issue is addressed, perform a controlled restart in accordance with the cluster's operational procedures.
4. Correct any identified CoreDNS configuration issues, plugin errors, resource constraints, or other underlying problems that contributed to the panic.
5. Continue monitoring CoreDNS pod health, restart counts, logs, DNS resolution, and panic metrics to ensure the issue does not recur.

---

## Validation

1. DNS Operator is Available and not Degraded.

```bash
oc get co dns
```

2. CoreDNS pods are Running and Ready.

```bash
oc get pods -n openshift-dns
```

3. Desired, current, and ready pod counts match.

```bash
oc get daemonset dns-default -n openshift-dns
```

4. No recurring panic messages.

```bash
oc logs -n openshift-dns <pod-name> -c dns --since=30m
```

5. Internal DNS resolution succeeds.

```bash
oc exec -n <application-namespace> <pod-name> -- getent hosts kubernetes.default.svc
```
6. CoreDNSPanicking alert is no longer Firing.
Check OpenShift Console → Observe → Alerting
